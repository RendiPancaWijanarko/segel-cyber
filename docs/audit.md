# SEGEL Technical Audit & Gap Analysis

**Authoritative References**: PRD v2.0 (Deliverable A), Technical Architecture Specification (TAS / Deliverable B), MVP Development Blueprint (MDB / Deliverable C).  
**Audit Scope**: Complete independent audit mapping every official P0 Functional Requirement (`FR`), Security Requirement (`SEC`), and Attack Test (`AT`) ID against actual source code and test suite implementations.  
**Compliance Scope**: Claims of "100% compliant" in legacy docs were identified as synthetic. SEGEL's verified compliance is strictly test-backed (310 passing automated tests) and bounded by the gap analysis detailed below.  
**Constraint Followed**: Read-only audit; zero application code modified.

## 2. Contradictions Between Code and Documentation

### 2.1. SEC-004 Key Isolation Violation in Release Desk
* **Documentation Claim** (`docs/ARCHITECTURE.md`, `docs/SECURITY_MODEL.md`, `src/release_desk/app.py:5`): "No key held by the Release Desk process exists. The Desk handles requests and public evidence only. Signing occurs in separate processes."
* **Actual Code Implementation** ([`src/release_desk/app.py:121-185`](../src/release_desk/app.py#L121)): `DemoState` generates and stores in heap memory: `author_key`, `builder_key`, `inspector_key`, `approver_keys[0..2]`, `ledger_key`, and `witness_key`. The `create_release` endpoint ([`app.py:245-299`](../src/release_desk/app.py#L245)) directly calls `sign_manifest()`, `sign_origin()`, `sign_inspect()`, `approver_sign()`, `sign_checkpoint()`, and `cosign_checkpoint()` in a single HTTP request handler.
* **Impact**: Zero trust boundary. A compromised web application compromises the entire signing authority and ledger witness.

### 2.2. SEC-017 Misattribution and Complete Absence of Local Hash-Chained Audit Log
* **Documentation Claim** (PRD v2.0 Table 34 SEC-017): "A local hash-chained audit log MUST record security-relevant events without secrets."
* **Code Contradiction** ([`src/builder/builder.py:10`](../src/builder/builder.py#L10)): Source code header mistakenly states: *"Per SEC-017: Package creation uses sorted paths, fixed mtime, fixed uid/gid."* (Deterministic packaging is actually FR-011).
* **Impact**: The actual SEC-017 requirement (a local hash-chained audit log on the Receiver) is **completely missing from the codebase**, while code comments falsely cite SEC-017 as satisfied.

### 2.3. Severe Mislabling of Adversarial Tests in `tests/adversarial/test_adversarial.py`
The test suite claims to implement the PRD v2.0 AT-series, but systematically binds test implementations to the wrong requirement numbers:
1. `test_at016_credential_reference_warns`: PRD Table 50 defines AT-016 as *"AI cites a non-existent capability ID"*. The test tests credential reference warnings.
2. `test_at019_ai_failure_recorded`: PRD Table 50 defines AT-019 as *"Injection in purpose text and configuration values (20 cases)"*. The test tests AI failure recording (which is AT-018).
3. `test_at026_path_traversal_blocked`: PRD Table 50 defines AT-026 as *"Disk exhaustion at preflight or during staging"*. The test tests path traversal (which is AT-027).
4. `test_at028_executable_blocked`: PRD Table 50 defines AT-028 as *"Decompression bomb"*. The test tests executable extension blocking.
5. `test_at029_empty_release_blocked`: PRD Table 50 defines AT-029 as *"Two concurrent deployments on one target"*. The test tests empty bundle rejection.
6. `test_at030_null_byte_in_path_blocked`: PRD Table 50 defines AT-030 as *"Network or power loss mid-deployment, injected at every journal step"*. The test tests null byte paths.
* **Impact**: Gives false security assurance that disk exhaustion, decompression bombs, concurrent deployments, power failure journaling, and prompt injections are tested when they are not.

### 2.4. FR-052 Ledger Event Types Specification Mismatch
* **Documentation Claim** (PRD v2.0 Table 17 FR-052): Event types MUST include `candidate_recorded`, `release_promoted`, `hold`, `hold_lifted`, `key_revoked`, `trust_updated`, and `receipt_ingested`.

* **Impact**: `hold_lifted` and `receipt_ingested` are rejected as invalid schemas; `hold` is named `hold_issued`.

### 2.5. FR-051 Autonomous Ledger Evidence Verification Not Implemented

## 3. Top 10 Highest-Risk Gaps

### 1. Private Key Colocation in Web Process (SEC-004)
* **Risk Severity**: **CRITICAL**
* **Root Cause**: [`src/release_desk/app.py:121-185`](../src/release_desk/app.py#L121) holds Author, Builder, Inspector, Approver 1 & 2, Ledger, and Witness private keys in the web server memory.
* **Operational Impact**: Complete elimination of separation of duties. Any RCE, memory disclosure, or SSRF vulnerability against the FastAPI web application yields total compromise of all trust domains, allowing an attacker to forge release passports and cosign ledger entries.
* **Mitigation Guidance**: Refactor `app.py` to strip all `KeyPair` objects and private keys. The Desk must solely accept externally signed DSSE envelopes via API or file upload, communicating with local signers over air-gapped QR or IPC channels.

### 2. Bypass of Ledger Checkpoint Signature Verification in Passport (AT-022)
* **Risk Severity**: **CRITICAL**
* **Root Cause**: [`src/segel_core/verification/passport.py:375-378`](../src/segel_core/verification/passport.py#L375) fetches ledger keys from trust context but does not verify the signature on `note_text`, checking only Merkle tree inclusion.
* **Operational Impact**: An adversary with control of distribution media can present arbitrary checkpoints signed by unknown keys; as long as the Merkle inclusion math computes against the untrusted root hash, the Receiver accepts the record stamp as valid.
* **Mitigation Guidance**: Implement DSSE/note-text signature verification in `verify_passport()` asserting that `signed_checkpoint.ledger_signature` is valid under an authorized non-revoked ledger key before checking inclusion proofs.

### 3. Ledger Appends Without Evidence Validation (FR-051)
* **Risk Severity**: **HIGH**
* **Root Cause**: [`src/ledger/ledger.py:162-202`](../src/ledger/ledger.py#L162) appends any JSON payload matching valid event type strings without checking underlying signatures or validity.
* **Operational Impact**: The transparency ledger ceases to act as an autonomous trust gate. Malformed, unapproved, or forged events submitted directly to the ledger service are permanently recorded into the Merkle tree and cosigned by witnesses.
* **Mitigation Guidance**: Add an autonomous verification layer in `TransparencyLedger.append()` that parses the DSSE envelopes of candidate releases, verifies approval threshold validity, and rejects unverified events.

### 4. Absence of Deployment Concurrency Mutual Exclusion (FR-086, AT-029)
* **Risk Severity**: **HIGH**
* **Root Cause**: Neither [`src/receiver/receiver.py`](../src/receiver/receiver.py#L117) nor [`src/receiver/adapter/baseline.py`](../src/receiver/adapter/baseline.py#L88) acquires a cross-process mutual exclusion file lock on `deploy_root`.
* **Operational Impact**: Two concurrent deployment invocations on the same unit will race during staging, backup, and apply phases, resulting in catastrophic configuration corruption, inconsistent rollbacks, and invalid post-state digests.
* **Mitigation Guidance**: Implement OS-level non-blocking file locking (`portalocker` or `fcntl`/`msvcrt`) on `<deploy_root>/.lock` in `Receiver.verify_and_deploy()`. Refuse secondary concurrent deployments immediately.

### 5. Missing Persistent Crash-Proof Deployment Journaling (FR-083, AT-030)
* **Risk Severity**: **HIGH**
* **Root Cause**: Deployment lifecycle progress is stored purely in memory in `DeploymentState` ([`src/receiver/adapter/baseline.py:76`](../src/receiver/adapter/baseline.py#L76)).
* **Operational Impact**: If power is cut mid-apply (between step 6 and step 8), the system reboots with no record of the incomplete operation. The target directory remains in an invalid mixed state, and the unit fails open or crashes without rollback.
* **Mitigation Guidance**: Introduce an atomic write-ahead journal file (`deploy_journal.json`) updated at each of the 10 lifecycle steps. On receiver startup, inspect the journal and automatically trigger rollback if a deployment was interrupted.

### 6. Ignored Deployment Adapter Digest Pinning (FR-081, SEC-015, AT-039)
* **Risk Severity**: **HIGH**
* **Root Cause**: [`VerificationPolicy.allowed_adapters`](../src/segel_core/schemas/trust.py#L206) is never checked by `receiver.py` or `passport.py`.
* **Operational Impact**: An attacker can substitute or tamper with the deployment adapter binary or script. The Receiver accepts any adapter identity without validating its cryptographic SHA-256 digest against the signed policy.
* **Mitigation Guidance**: Compute the SHA-256 digest of the runtime adapter implementation during receiver initialization and verify that `(adapter_id, digest)` matches an entry in `trust_ctx.policy.allowed_adapters`.

### 7. Broken Ledger-Index Key Revocation Ordering (FR-063, SEC-012, AT-010)
* **Risk Severity**: **MEDIUM**
* **Root Cause**: [`src/segel_core/verification/trust.py:131`](../src/segel_core/verification/trust.py#L131) implements `is_key_revoked_at_index()`, but it is dead code. `get_keys_for_role()` globally blacklists all keys present in `snapshot.revoked_keys`.
* **Operational Impact**: Revoking an author or approver key invalidates all past, legitimately deployed releases previously verified against that key, causing denial of service and invalid recovery states across offline units.
* **Mitigation Guidance**: Pass the ledger entry index of each evidence envelope into key verification lookups. Query `is_key_revoked_at_index(key_id, evidence_index)` so that evidence recorded prior to `revoked_at_index` remains accepted.

### 8. Total Absence of Local Hash-Chained Audit Logging (SEC-017)
* **Risk Severity**: **MEDIUM**
* **Root Cause**: No audit logging module exists in `src/receiver/` or `src/segel_core/`.
* **Operational Impact**: Security-critical events (verification failures, rejected releases, epoch mismatches, recovery triggers) leave no tamper-evident forensic trail on the air-gapped unit. Post-incident forensics cannot verify whether a unit was targeted.
* **Mitigation Guidance**: Implement a dedicated `AuditLogger` class writing append-only, SHA-256 hash-chained JSON records (`prev_hash`, `timestamp`, `event_type`, `details`, `curr_hash`) to `<state_dir>/audit.log`.

### 9. Stubbed AI Advisory with Missing Adversarial Defenses (FR-022, AT-016, AT-019)
* **Risk Severity**: **MEDIUM**
* **Root Cause**: [`_run_ai_advisory()`](../src/inspector/inspector.py#L345) raises `NotImplementedError`. Prompt injection defenses and hallucinated capability validations do not exist.
* **Operational Impact**: While the deterministic policy engine protects core authorization, AI advisory features promised in PRD v2.0 are non-functional. If enabled with a live Ollama instance, the absence of prompt injection sanitization allows adversarial inputs to manipulate findings.
* **Mitigation Guidance**: Implement Ollama HTTP client in `_run_ai_advisory()`; sanitize prompt templates; implement AT-016 filter discarding any AI finding citing a capability not present in `capabilities`; add the 20-case prompt injection test corpus (`AT-019`).

### 10. Missing Offline Trust Update Package Mechanism (FR-066, SEC-035, AT-042)
* **Risk Severity**: **MEDIUM**
* **Root Cause**: `TrustUpdatePackage` schema and root-rotation chain verification are completely absent from the codebase.
* **Operational Impact**: Air-gapped receivers cannot securely rotate root trust keys or update verification policies without manual out-of-band state replacement, creating operational vulnerability to operator error or unauthorized state tampering.
* **Mitigation Guidance**: Create `TrustUpdatePackage` schema bundling new root, policy, snapshot, and Merkle consistency proofs. Implement chain verification requiring threshold signatures from both the previous root and the new root before state transition.
